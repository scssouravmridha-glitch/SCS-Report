# SCS Monthly Report — JSON ব্যাকআপসহ আপডেট

এই প্যাকেজ স্ক্রিনশটে দেখানো সাইটের deploy করা পাবলিক HTML ও তার **বর্তমান** Supabase গঠন (`scs_manual_data`, `scs_manual_history`, `scs_orders`, `scs_attendance`, `scs_settings`, `scs-files`) ধরে তৈরি। আগের `scs-supabase.zip`-এর `scs_months`-ভিত্তিক SQL বা ব্যাকআপ এই সংস্করণে ব্যবহার করবেন না। স্ক্রিনশটের ভাসমান লাইভ-ডেটা বাটন সরানো হয়েছে; Admin-এর ডেটা ম্যানেজার রাখা হয়েছে। Netlify ব্যাজ বন্ধের তথ্য নিচে আছে।

## ১. প্রথমে Supabase-এ ব্যাকআপ ফাংশন যোগ করুন

1. বিদ্যমান ডাটার আলাদা ব্যাকআপ রাখুন। Supabase Dashboard-এ `ddgdjuxrpqpluzegzswj` প্রজেক্ট খুলুন।
2. **SQL Editor → New query** খুলুন। এই প্যাকেজের `supabase/backup-functions.sql` ফাইলের পুরো কোড পেস্ট করে **Run** করুন। এটি ব্যাকআপ, রিস্টোর, পুরোনো JSON ইমপোর্ট, রিসেট ফাংশন ও প্রয়োজনীয় sequence permission তৈরি করে; ইনস্টল করার সময় ডাটা মুছে না। আগের সংস্করণের SQL চালিয়ে থাকলেও এই সম্পূর্ণ আপডেটেড ফাইলটি আবার Run করা জরুরি। স্ক্রিনশটে `scs_export_snapshot ... schema cache` দেখালে ফাংশন ইনস্টল হয়নি; Run করার পর কিছুক্ষণ অপেক্ষা করে পেজ রিফ্রেশ করুন।
3. স্বাভাবিক অবস্থায় `original-schema.sql` চালানোর দরকার নেই: এতে বর্তমান সাইটের মূল schema রাখা হয়েছে কেবল ডাটাবেস পুনর্গঠনের প্রয়োজনে। ভুল প্রজেক্টে SQL চালাবেন না।

> **নিরাপত্তা:** আপনার বিদ্যমান সাইটে Supabase-এর anon/publishable key দিয়ে টেবিলে পড়া ও লেখার উন্মুক্ত অনুমতি রয়েছে; Admin PIN শুধু UI-তে কাজ করে। ফলে যে কেউ API ব্যবহার করে ডাটা পড়তে, বদলাতে, রিস্টোর বা রিসেট ফাংশন চালাতে পারে; রিসেটের PIN ও ব্যাকআপ যাচাই শুধু অ্যাপের UI-তে বাধ্যতামূলক, সরাসরি API ব্যবহার আটকায় না। ব্যাকআপ ফাংশন এই উন্মুক্ত মডেলের উপরই কাজ করে; বাস্তব সুরক্ষার জন্য Supabase Auth ও সীমিত RLS আলাদাভাবে প্রয়োজন। ব্যাকআপ ফাইলে সংবেদনশীল তথ্য ও PIN-এর hash থাকতে পারে—ব্যক্তিগত স্থানে রাখুন।

## ২. GitHub → Netlify

1. ZIP extract করে `scs-live-update` ফোল্ডারের **ভিতরের** `index.html`, `backup-tools.js`, `legacy-format.js`, `netlify.toml`, `supabase` ফোল্ডার এবং `README.md` GitHub repository-র root-এ দিন।
2. Netlify-তে repository সংযুক্ত করুন। **Build command** খালি এবং **Publish directory** `.` রাখুন।
3. আগে deploy preview-তে PIN লগইন, Admin ও ব্যাকআপ কার্ড পরীক্ষা করুন। পুরনো ও নতুন deploy-এর ডাটাবেস একই: পরীক্ষার সময় প্রকৃত ডাটা বদলানো এড়িয়ে চলুন।
4. ডান দিকের Netlify ব্যাজ দেখা গেলে Dashboard → **Project configuration → General → Powered by Netlify badge → Off → Save** করুন। Netlify নিজে ব্যাজ inject করে, তাই কোডের CSS fallback সব ভবিষ্যৎ সংস্করণে কাজ করবে এমন নিশ্চয়তা নেই।

## ৩. মাস, বছর বা লাইফটাইম JSON এক্সপোর্ট

1. Admin PIN দিয়ে প্রবেশ করুন → **Admin → 5. Logo, Control & Backup → Permissions, Backup & Reset → JSON ব্যাকআপ, রিস্টোর ও Drive**।
2. **নির্দিষ্ট মাস**, **নির্দিষ্ট বছর (সব মাস)** অথবা **লাইফটাইম (সব ডাটা)** বেছে **JSON ডাউনলোড** চাপুন। বছর যেকোনো চার অঙ্কের বছর লেখা যায়।
3. নতুন ফাইলে আপনার পুরোনো ফরম্যাটের মতো `app`, `format`, `version`, `scope`, `exportedAt`, `months`, `settings` থাকে। সম্পূর্ণ Supabase পুনরুদ্ধারের জন্য অতিরিক্ত `scsSupabase` অংশে সব রিপোর্টের ম্যানুয়াল ডাটা, সব অর্ডার, অ্যাটেনডেন্স, সেটিংস, ইতিহাস এবং `scs-files` bucket-এর ফাইল base64 হিসেবে থাকে। আগের অ্যাপ অতিরিক্ত অংশ ব্যবহার করে কি না নিশ্চিত নয়। `exportedAt`-এ UTC সময় এবং ফাইলের নামেও সময় থাকে।
4. মাস/বছরের ফাইলে সংশ্লিষ্ট মাসের রিপোর্ট, ইতিহাস ও অ্যাটেনডেন্স থাকে; অর্ডার নম্বর বা ডেলিভারি/অর্ডার তারিখ থেকে মাস নির্ণয় করা হয়। যেসব অর্ডারের মাস বোঝা যায় না সেগুলো বাদ যায় এবং সংখ্যা কার্ডে দেখায়। সেটিংস ও Storage ফাইল প্রতিটি স্কোপে থাকে। সবসময় সম্পূর্ণ ব্যাকআপের জন্য লাইফটাইম নিন।

## ৪. JSON রিস্টোর

1. আগে বর্তমান লাইফটাইম JSON ডাউনলোড করুন। কাজের সময় অন্য ডিভাইস/ট্যাব বন্ধ রাখুন, যাতে রিস্টোরের সঙ্গে একযোগে ডাটা পরিবর্তন না হয়।
2. Admin-এ JSON ফাইল বেছে **ফাইল থেকে রিস্টোর** চাপুন এবং নিশ্চিত করুন। আপনার পুরোনো `format: scs-backup`, `version: 2`, `months`, `settings` ফাইল; নতুন এক্সপোর্ট করা একই মূল ফরম্যাটের ফাইল; এবং আগের `type: scs-live-backup` ফাইল গ্রহণ করা হয়।
3. **লাইফটাইম** ফাইল বর্তমান পাঁচটি টেবিলের ডাটা ব্যাকআপের ডাটা দিয়ে প্রতিস্থাপন করে—ব্যাকআপের পর যুক্ত হওয়া রেকর্ড মুছে যাবে। **মাস/বছর** ফাইল একই primary key/ID-এর রেকর্ড প্রতিস্থাপন করে; ফাইলে নেই এমন রেকর্ড রাখে। অন্য database থেকে আনা ID সংঘর্ষে সংশ্লিষ্ট রেকর্ড প্রতিস্থাপিত হতে পারে।
4. টেবিল রিস্টোর একটি ডাটাবেস transaction-এ হয়। Storage ফাইল আগে আলাদাভাবে আপলোড হয়—মিডিয়া ও ডাটাবেস একসাথে transaction নয়, ব্যর্থ হলে কিছু ফাইল বদলে যেতে পারে। অতিরিক্ত Storage ফাইল মুছে ফেলা হয় না। সাইটের ট্রিগারের কারণে revision ও updated timestamp পরিবর্তিত হতে পারে।
5. সম্পন্ন হলে সব ডিভাইসে পেজ রিফ্রেশ করুন এবং রিপোর্ট, অর্ডার, অ্যাটেনডেন্স, লোগো/গান পরীক্ষা করুন।

### পুরোনো JSON রিস্টোরের সীমা ও আচরণ

আপনার দেওয়া `scs-backup` v2 ফাইলে থাকা মাসের রিপোর্ট ও সেটিংস ইমপোর্ট হয়; অর্ডারগুলো `sheetRow` ID অনুযায়ী যুক্ত/আপডেট হয় এবং ফাইলে থাকা মাসের অ্যাটেনডেন্স প্রতিস্থাপিত হয়। অন্য মাস ও অন্য অর্ডার মোছা হয় না। অর্ডার ID বিদ্যমান ভিন্ন অর্ডারের সঙ্গে সংঘর্ষ করলে ইমপোর্ট বাতিল হয়; সার্ভারের সব পরিবর্তন transaction-এ rollback হয়। একই ফাইল বারবার ইমপোর্ট করলে একই অর্ডার পুনরায় যোগ হয় না। ফাইলে না থাকা ইতিহাস ও binary লোগো/গান ফিরবে না; পুরোনো Drive file ID থাকলেও সেটি নিজে binary ফাইল নয়। প্রয়োজনে লোগো/গান আবার আপলোড করুন। রিস্টোরের আগে বর্তমান ব্যাকআপ রাখুন এবং শেষে পেজ রিফ্রেশ করে রিপোর্ট পরীক্ষা করুন।

## ৫. নির্দিষ্ট ব্যবধানে Google Drive ব্যাকআপ

1. ডাটাবেসে ধাপ ১ এবং সাইট deploy শেষ করুন। Google Drive-এ একটি **ফোল্ডার** তৈরি করে তার লিংক Admin-এর Drive বাক্সে পেস্ট করে ১, ২, ৪, ৬, ১২ বা ২৪ ঘণ্টা ব্যবধান নির্বাচন করুন → **ফোল্ডার ও সময় সেভ করুন**। ফোল্ডারটি ব্যক্তিগত রাখুন।
2. [script.google.com](https://script.google.com/) → **New project**। `supabase/drive-backup.gs`-এর পুরো কোড পেস্ট করে Save করুন। যেই Google অ্যাকাউন্ট দিয়ে স্ক্রিপ্ট চালাবেন সেটির ওই ফোল্ডারে লেখার অনুমতি থাকতে হবে।
3. ফাংশন তালিকা থেকে `setupHourlyBackup` বেছে **Run** করুন; Drive ও external URL permission অনুমোদন করুন। এটি ঘণ্টায় একবার পরীক্ষা করার trigger তৈরি করে এখনই একটি পরীক্ষামূলক ব্যাকআপ নেয়। প্রতি ঘণ্টায় স্ক্রিপ্ট নির্বাচিত ব্যবধান পূর্ণ হয়েছে কি না দেখে, হয়ে থাকলে লাইফটাইম ব্যাকআপ নেয়। আগে পুরনো সংস্করণের script ব্যবহার করে থাকলে পুরো স্ক্রিপ্ট প্রতিস্থাপন করে `setupHourlyBackup` আবার চালান। ব্যবধান পরিবর্তন করলে অ্যাপে সেভ করলেই পরের চেক থেকে প্রযোজ্য হয়। ফোল্ডার সেভ করলেই trigger নিজে তৈরি হয় না। আগের Apps Script প্রজেক্ট ব্যবহার করলে নতুন ফাইলের পুরো কোড দিয়ে প্রতিস্থাপন করে `setupHourlyBackup` আবার চালান, নইলে পুরোনো ফরম্যাটে ব্যাকআপ হতে থাকবে।
4. Apps Script-এর **Executions** ও Drive ফোল্ডার যাচাই করুন। `SCS-Backup_YYYY-MM-DD_HH-mm-ss.json` ফাইল তৈরি হলে তবেই সফল হয়েছে; একটি নিরাপদ পৃথক পরিবেশে রিস্টোর পরীক্ষা করুন। সময় ফাইলের নামে Asia/Dhaka এবং JSON-এর `exportedAt` UTC। একই JSON Admin রিস্টোরে ব্যবহার করা যায়।
5. `backupNow` ফাংশন চালিয়ে তখনই ব্যাকআপ নিন। `stopHourlyBackup` ফাংশন দিয়ে ট্রিগার বন্ধ করতে পারবেন। পুরনো Drive ব্যাকআপ স্বয়ংক্রিয়ভাবে মোছা হয় না; Drive-এর জায়গা পর্যবেক্ষণ করুন।

## ৬. CSV দিয়ে অর্ডার ও অ্যাটেনডেন্স ইমপোর্ট

Admin → **1. Supabase Data → ডেটা ম্যানেজার খুলুন**। অর্ডার বা অ্যাটেনডেন্স ট্যাব বেছে **পেস্ট / CSV ইমপোর্ট** চাপুন; CSV ফাইল নির্বাচন করুন অথবা হেডারসহ CSV/শিটের ডাটা পেস্ট করুন। অ্যাটেনডেন্সের জন্য আগে সঠিক মাস বেছে নিন। তথ্য যাচাই করে **ইমপোর্ট করুন** চাপুন। এটি নতুন সারি যোগ করে, আগের সারি স্বয়ংক্রিয়ভাবে শনাক্ত করে বাদ দেয় না; একই ফাইল বারবার দিলে ডুপ্লিকেট হতে পারে। বড় ইমপোর্ট একাধিক ভাগে সেভ হয়, মাঝপথে ব্যর্থ হলে কিছু সারি যুক্ত থাকতে পারে।

## ৭. লাইফটাইম ব্যাকআপ যাচাই করে সম্পূর্ণ ডাটাবেস রিসেট

1. Supabase SQL Editor-এ এই সংস্করণের `backup-functions.sql` আবার চালিয়ে নতুন রিসেট ফাংশন যুক্ত করুন। অন্য সব ডিভাইস ও ট্যাব বন্ধ করুন।
2. Admin → **5. Logo, Control & Backup → Permissions, Backup & Reset**-এ **লাইফটাইম ব্যাকআপ ডাউনলোড** চাপুন। ফাইলটি নিরাপদ স্থানে সেভ করুন।
3. ওই সেভ করা ফাইলটি আবার নির্বাচন করে **ফাইল যাচাই করুন** চাপুন। ফাইল, লাইভ টেবিল এবং মিডিয়া মিললে রিসেট বাটন সক্রিয় হবে। রিসেটের আগে টেবিল বদলালে সার্ভার রিসেট বাতিল করে; নতুন ব্যাকআপ নিতে হবে।
4. রিসেট চাপার পর সতর্কতা পড়ুন, Admin PIN দিন এবং `RESET` লিখে নিশ্চিত করুন। পাঁচটি ডাটাবেস টেবিলের ডাটা মুছে যায়, কিন্তু সতর্কতা হিসেবে Storage-এর ফাইলগুলি মুছে ফেলা হয় না। রিসেট একটি database transaction; অন্য ট্যাবের সেভ চলতে থাকলে রিসেটের পর আবার ডাটা তৈরি হতে পারে—তাই অন্য ডিভাইস বন্ধ রাখা জরুরি।
5. সেটিংস মুছে যাওয়ায় অ্যাপ ডিফল্ট PIN ব্যবহার করতে পারে এবং Drive ফোল্ডার সেটিংস সরবে; ব্যাকআপ চলা বন্ধ হতে পারে। ব্যাকআপ JSON থেকে রিস্টোর করুন অথবা ফোল্ডার আবার সেট করুন। যাচাই করা JSON একাধিক নিরাপদ স্থানে রাখুন।

**গুরুত্বপূর্ণ:** PIN ও সেভ করা ফাইল যাচাই UI-তে কার্যকর। বিদ্যমান উন্মুক্ত RLS-এর কারণে এটি সরাসরি Supabase API-এর নিরাপত্তা বাধা নয়; Auth ও কঠোর RLS ছাড়া অন্য কেউ API দিয়ে ডাটা মুছতে পারে।

**ব্যাকআপের সীমাবদ্ধতা:** Google trigger আনুমানিকভাবে চলে; ব্যাকআপ সময় বা ব্যবধান ঠিক ঘড়ির কাঁটা অনুযায়ী হওয়ার নিশ্চয়তা নেই। নেটওয়ার্ক, অনুমতি, Drive quota, Apps Script execution time/memory এবং বড় JSON বা Supabase response সীমার কারণে ব্যর্থ হতে পারে। ডাটাবেস টেবিলগুলো একক PostgreSQL statement snapshot হলেও Storage আলাদা সময়ে পড়া হয়। বাহ্যিক লিংকের ফাইল বা লোকাল browser-only ডাটা এতে থাকে না; ডাটাবেস হারালে আগে একই schema ও ফাংশন পুনর্গঠন এবং `scs-files` bucket/permissions সেট করতে হবে। Executions, Drive ফাইল, আকার ও রিস্টোর নিয়মিত পরীক্ষা করুন এবং অন্যত্র কপিও রাখুন। কোনো ব্যাকআপ ব্যবস্থা শতভাগ ডাটা না হারানোর নিশ্চয়তা দেয় না।
